## 설계

### 근거 장부 상세화 (`ledger`)

- 근거 판정 호출 안에서 질문에 필요한 정보 항목을 `{"item", "status": FOUND | MISSING}` 목록으로 함께 받는다. 판정 JSON 스키마에 `ledger` 칸을 서술 다음, 판정 앞에 둔다(키 순서 reasoning → ledger → decision → missing → answer). **판정 호출 수는 늘지 않는다.**
- RETRIEVE면 빠진 정보를 장부의 MISSING 항목으로 정하고(MISSING이 없으면 모델이 쓴 `missing`), 한 번의 재검색은 첫 MISSING 항목 하나만 검색어로 쓴다(`ConditionalHooks.ledger`).
- 장부를 끄면 판정 프롬프트·스키마·파싱이 v2와 글자까지 같다(13개 조합 확인). 동결 M의 동작은 바뀌지 않는다.
- JSON 형식에서만 쓴다(태그 형식에 켜면 오류).

### 동적 압축량 (`dynamic_m`)

- 질문 속 고유명사 덩어리(첫 단어를 뺀, 대문자로 시작하는 연속 단어 묶음)가 하나 이하면 남길 문장 창 수를 `max(1, m // 2)`(m=7 → 3)로 줄이고, 둘 이상이면 m을 그대로 둔다. 질문 글자만 보며 문항 유형은 쓰지 않는다. 모델을 부르지 않는다.
- 규칙을 정한 근거 (개발 세트 검색형 40문항, k=5, 모델 없이 검색·압축만):

| 질문 특징 | 문항 | m=3 근거 글자 | m=7 근거 글자 | 정답 문자열 남음 m=3 / m=7 | 근거 문장 남음 m=3 / m=7 |
|---|---|---|---|---|---|
| 고유명사 덩어리 ≤ 1 | 20 | 682 | 1325 | 7/10 / 7/10 | 5/5 / 5/5 |
| 고유명사 덩어리 ≥ 2 | 20 | 597 | 1422 | 12/20 / 17/20 | 21/32 / 29/32 |

고유명사가 하나 이하인 질문은 m을 줄여도 근거에 남는 정답·근거 문장이 같았고, 둘 이상인 질문은 m을 줄이면 근거가 빠졌다. 이 분석과 규칙 선택은 개발 세트에서 했으므로 같은 dev로 채택을 판정할 때 낙관적일 수 있다.

## 결정

**두 부품 모두 기각한다. M은 동결 구성(v2) 그대로이며, 조건부 부품을 넣지 않는다.** 실험 전에 적은 기준을 그대로 적용했다.

- **근거 장부 상세화: 기각.** 공통 조건을 어겼다(HotpotQA 5 → 4, SQuAD 답 있음 5 → 2). 목표 지표도 둘 다 반대 방향이다(HotpotQA 정답 감소, HotpotQA 호출 ×1.44). 비용도 호출 ×1.26, 입력 토큰 ×1.49, 시간 ×1.7로 모두 늘었다.
- **동적 압축량: 기각.** 공통 조건은 통과했다(유형별 정답 모두 같음, 정오 60/60 같음). 하지만 목표 지표가 ×0.953으로 기준 ×0.9에 못 미쳤다. 줄인 20문항에서는 ×0.87이었지만, 압축을 거치지 않는 GSM8K와 판정 프롬프트의 고정 부분 때문에 전체 평균에서 효과가 묽어졌다. 실험 뒤에 기준을 "검색형만"으로 바꾸지 않는다. 검색형만 봐도 ×0.942로 기준에 못 미친다.

코드는 남기되 기본값은 꺼져 있다. `MComponents(ledger=False, dynamic_m=False)`가 기본이고, 장부를 끄면 판정 프롬프트·스키마·파싱이 v2와 같다. `run_eval`의 `m_ledger`·`m_dynamic_m` 이름은 이 실험을 재현하는 용도이며, 본 측정·절제 묶음에는 넣지 않는다.

## 이 결과를 읽을 때 주의할 점

- dev 60문항 한 라운드의 결과다. 장부의 정답 차이(6 대 4)는 우연 범위 안이다(p = 0.75). 기각 근거는 정확도가 아니라 공통 조건 위반과 비용 증가다.
- 동적 압축량의 규칙(고유명사 덩어리 ≤ 1이면 m//2)은 같은 dev에서 골랐다. 그런데도 기준을 넘지 못했으므로 기각 판단은 보수적이다.
- 장부는 판정 프롬프트 한 가지 문구로만 시험했다. 장부 문구 튜닝은 같은 dev로 반복 튜닝하는 것이 되고 M 동결(11/27)과도 맞지 않아 하지 않는다.
