# D-4 `cap.judge` 출력 상한 민감도 실험 — 선행 작업 대기

2026-11-27 기준. 이 문서는 실험 결과가 아니라 실행 가능성 점검 기록이다. 96 / 160 / 256의 결과를 측정하지 않았고, 최적값도 선정하지 않았다.

## 목적과 선행 조건

동일한 M 개발 세트 실행에서 근거 판정 단계의 `cap.judge`만 바꿔 정확도, 출력 토큰, 잘림을 비교한다. [SPEC §7](../SPEC.md)의 목적은 가장 작은 상한 선정이 아니라 **잘림 없이 정확도가 유지되는 범위** 확인이다. 선행 조건은 PR A-5b의 M 통합과 개발 세트 완주다([구현 계획](../IMPLEMENTATION_PLAN.md)).

현재 체크아웃(`Dongsub` @ `f94acf3`)에는 `src/meba/graph.py`와 `tests/test_graph.py`가 없고, `src/meba/conditional/`에는 `.gitkeep`만 있다. [실행 스크립트](../../scripts/run_eval.py)의 `m` 등록은 아직 없는 `src.meba.graph:build_m`을 가리킨다. [진행 기록](../progress.md)도 A-5a/A-5b를 미완료로 표시한다. 따라서 M 개발 세트를 실행하는 파이프라인이 없다. 이 환경에는 Ollama 실행 파일, `pytest`, LangChain, PyYAML도 설치되어 있지 않다. 선행 작업을 임의로 대신 구현하거나 결과를 만들어 넣지 않았다.

## 확인한 설정과 적용 방식

기본값은 [기본 설정](../../configs/default.yaml)의 `cap.judge: 256`이다. [설정 로더](../../src/config/settings.py)는 이를 `Settings.cap.judge`로 읽고, [근거 판정 호출](../../src/meba/judge.py)은 `BudgetedLLM`을 통해 `judge` 단계로 호출한다. [출력 예산](../../src/meba/budget.py)은 해당 상한을 `num_predict`에 적용하고 잘림이면 설정의 `cap.retry_multiplier`로 한 번 재시도한다. P1 로그에는 M의 `judge` 단계가 없으므로 D-3 수치로 세 조건의 성능을 추정할 수 없다.

## 예정된 비교와 지표

세 조건은 동결 `data/frozen/dev.jsonl` 60문항을 사용하며, 모델·temperature·시드·프롬프트·검색 설정(`k`, `m`)·채점기·타임아웃·실행 환경을 같게 둔다. 비교 전에는 B-4가 제출한 `k=5`, `m=7`이 M의 공통 설정에 반영됐는지도 확인해야 한다. 현재 `configs/default.yaml`은 임시값 `k=3`, `m=3`이다. 별도 설정 파일 세 개는 M 통합 뒤 공통 설정을 복사해 `cap.judge`만 바꾸고, 각각 독립된 개발 라운드 로그와 설정 스냅샷으로 보존한다. 기존 라운드에 다른 설정으로 이어 쓰지 않는다.

| 지표 | 계산식과 분모 | 96 | 160 | 256 |
|---|---|---|---|---|
| 전체 정확도·정답 수 | `correct=true` 건수 / 개발 문항 60개(워밍업·타임아웃 포함) | 미측정 | 미측정 | 미측정 |
| 유형별 정확도 | 유형별 정답 수 / 해당 유형 20개 | 미측정 | 미측정 | 미측정 |
| 평균·전체 출력 토큰 | 호출별 `output_tokens` 합 / 비용 대상 문항 수(각 조건 워밍업 제외); 합계도 함께 기록 | 미측정 | 미측정 | 미측정 |
| 실제 출력 잘림 건수·비율 | 모델 종료 사유가 길이 제한임이 확인된 `judge` 호출 수 / 종료 사유를 확인한 `judge` 호출 수 | 미측정 | 미측정 | 미측정 |
| 형식 오류율 | 파싱 실패한 `judge` 호출 수 / 파싱 결과가 기록된 `judge` 호출 수 | 미측정 | 미측정 | 미측정 |
| 실행 시간 | 워밍업 제외 문항의 `latency_s` 평균·합계, 타임아웃 건수 병기 | 미측정 | 미측정 | 미측정 |

잘림 재시도는 비용과 잘림 건수에 포함하고 정확도는 문항별 최종 답으로 센다. 현재 [콜백](../../src/config/callbacks.py)은 종료 사유가 `length`/`max_tokens`이거나 출력 토큰이 상한 이상이면 `truncated=true`로 기록하고, 종료 사유 자체는 `CallRecord`에 보존하지 않는다. 따라서 기존 `truncated` 값만으로는 요청된 **실제 잘림**을 확정할 수 없다. A-5b 통합 뒤 종료 사유와 원문을 개발 실험의 별도 추적 기록으로 확인하거나, 로그 규격을 바꾼다면 먼저 `docs/INTERFACES.md`를 수정해야 한다.

## 실행 명령과 결론

실행 명령은 **없다**. 현재 `python -m scripts.run_eval --bundle dev --round r1 --pipelines m`은 M 모듈 부재로 실행 불가다. 세 조건의 설정과 독립 로그 경로는 A-5b가 들어온 뒤 확정한다. 프로젝트에는 D-4 전용 정확도 유지 수치 기준이 없다. 비교할 때 [SPEC §6](../SPEC.md)의 조건부 부품 채택 기준인 유형별 순정답 수 비감소를 참고하고, 동일 문항의 256 조건과 비교해 정답→오답과 오답→정답을 기록한다. 이를 D-4의 확정 기준으로 새로 선언하지는 않는다. 세 조건의 실제 잘림과 정확도가 나오기 전에는 적합 범위나 최적값을 정할 수 없다.
