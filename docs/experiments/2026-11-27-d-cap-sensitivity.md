# D-4 `cap.judge` 출력 상한 민감도 — 개발 세트 실측 완료

2026-11-28 로컬 개발 세트 60문항씩 3조건 실측. **권장 후보는 160토큰**이다. 전체·유형별 정답 수가 256과 같고 확인된 판정 출력 잘림이 없으며, 256과 출력 토큰이 같았다. 한 라운드의 개발 세트 탐색 결과이므로 이후 M 구성 변경 시 재확인이 필요하다.

## 목적과 현재 환경

[SPEC §7](../SPEC.md)의 목적은 근거 판정 단계의 상한을 바꿔 **출력 잘림 없이 정확도가 유지되는 범위**를 찾는 것이다. A-5a/A-5b의 M 그래프와 개발 세트 완주 로그는 현재 브랜치(`Dongsub` @ `5e0a451`)에 있다. 기본 [설정](../../configs/default.yaml)은 `cap.judge=256`, `retrieval.k=5`, `compress.m=7`이다. `judge`는 [그래프](../../src/meba/graph.py)에서 [출력 예산](../../src/meba/budget.py)을 거쳐 ChatOllama로 호출된다.

실험 환경은 MacBook Air(M2, 통합 메모리 16GB), Python 3.12.16, Ollama 0.40.18, 설정의 `qwen2.5:7b-instruct-q4_K_M`(로컬 모델 ID `845dbda0ea48`), temperature 0, `num_ctx=8192`다. `RUN_META.json`의 git 커밋은 `5e0a451`이고 실험 코드·문서가 미커밋이라 `git_dirty=true`다. macOS에는 `nvidia-smi`가 없어 공통 로거의 GPU·VRAM 필드는 `null`이다. 외부 AI API는 사용하지 않았다.

## 조건과 재현 절차

[실험 계획](../../configs/d4_cap_sensitivity.json)은 기본 YAML 설정을 읽어 `cap.judge`만 96·160·256으로 교체한다. [실행기](../../scripts/run_cap_sensitivity.py)는 다른 설정이 같은 `Settings` 복사본을 만들고, 각 조건을 개발 세트 전체 60문항의 독립 라운드 `r20`·`r21`·`r22`로 실행한다. 각 라운드의 `RUN_META.json`에 전체 설정과 데이터 해시가 남는다. 모델·프롬프트·도구·시드·채점·타임아웃은 같다. 워밍업은 각 조건의 첫 문항 하나이며 비용에서만 제외한다.

```sh
.venv/bin/python -m scripts.run_cap_sensitivity --verify 2
.venv/bin/python -m scripts.run_cap_sensitivity
.venv/bin/python -m scripts.run_cap_sensitivity --summarize
```

정식 결과는 `results/runs/dev/r20/`·`r21/`·`r22/`에 문항마다 `m.jsonl`로 즉시 저장된다. 보조 `m_reason_trace.jsonl`에는 같은 문항의 모델 종료 사유와 원문을 저장한다. 같은 명령을 다시 실행하면 완료 문항은 건너뛴다. 검증 모드는 git 제외 대상인 `results/runs/_scratch/`에 쓴다. 동결 파일의 해시는 실행 전에 검사한다.

출력 상한에 도달했다는 사실만으로 **실제 잘림**을 확정하지 않는다. 공통 [콜백](../../src/config/callbacks.py)은 토큰 수가 상한에 닿아도 `truncated=true`로 표시할 수 있으므로, 실행기는 종료 사유를 별도 원문 로그에 보존하고 명시적인 길이 제한 종료만 확인된 잘림으로 센다. 종료 사유가 없거나 추적이 불완전한 호출은 미확인으로 따로 표시한다. 재시도 호출은 토큰 비용과 호출별 잘림 집계에 포함하고, 정확도는 최종 문항 답으로 센다. 이 분리 규칙은 [단위 테스트](../../tests/test_cap_sensitivity.py)로 확인했다.

## 출력 잘림 사례

96토큰 조건의 확인된 길이 제한 종료 4회는 `hotpotqa-0040` 1회, `hotpotqa-0048` 2회, `squad2-0058` 1회다. 모두 96토큰에서 끝났고 공통 예산 래퍼가 192토큰으로 한 번 재시도했다. `hotpotqa-0053`은 **96토큰에 도달했지만 종료 사유가 `stop`**이었다. 공통 콜백은 상한 도달만으로 `truncated=true`를 남겨 이 호출도 재시도했으나, 명시적 종료 사유 기준 실제 잘림에는 넣지 않았다. 이 사례 때문에 상한 도달 5회와 실제 잘림 4회를 구분한다. 세 라운드의 판정 호출 종료 사유는 모두 확인돼 미확인 수가 0이다.

96 조건의 잘림 사례들은 최종 오답이었지만, 160·256에서도 동일한 문항들이 오답이었다. 따라서 이번 로그만으로 그 문항들의 오답 원인을 잘림으로 단정하지 않는다. `gsm8k-0053`은 세 조건 모두 120초 시간 초과로 오답이며, 판정 상한이 아니라 공통 수학 경로에서 발생했다. 시간 초과 문항의 중단 전 호출·토큰은 회수되지 않아 비용 합계가 하한일 수 있다.

## 정확도 변화·토큰 효율·선정

이번 세 라운드에서는 정답 수와 유형별 정답 수가 모두 같았고, 256 기준으로 정답→오답·오답→정답으로 바뀐 문항이 없다. 96은 잘림이 4회라 제외한다. **시험한 값 중 160·256이 정확도 유지와 판정 잘림 0건을 만족**한다. 160과 256의 출력 합계가 모두 7,114토큰이므로 더 낮은 상한인 **160을 권장 후보**로 둔다. 96의 7,498토큰보다 384토큰(5.12%) 적은데, 96의 잘림 재시도와 상한 도달만으로 발생한 재시도 비용이 반영된 결과다. 160이 256보다 빠르다고 주장하지는 않는다. 평균 시간 차이는 한 라운드의 실행 변동을 포함한다.

보수적 후보 선정 규칙은 전체·유형별 정답 수가 256 이상이고, 확인된 판정 잘림과 종료 사유 미확인이 모두 0인 조건이다. 여러 후보면 워밍업 제외 평균 출력 토큰이 낮은 값을, 같으면 낮은 상한을 고른다. **96과 160 사이의 미시험 상한이 안전하다는 뜻은 아니다.** 기존 `r6`의 256 결과(31/60, 출력 8,151토큰)는 다른 세션·추적 방식의 참고치로만 두고 이 비교표에 섞지 않았다.

## 검증과 한계

소수 문항 검증 뒤 개발 60문항씩 세 라운드를 완주했고, 각 `m.jsonl`과 종료 사유 보조 로그가 60행이며 동결 해시도 일치한다. 설정 스냅샷에서 `cap.judge` 외 값은 같고, 실제 호출 기록의 `router`와 `finalize` 상한은 바뀌지 않았다. 설정·잘림 판정·후보 규칙의 [단위 테스트](../../tests/test_cap_sensitivity.py) 6개와 전체 테스트도 통과했다. 이 결과는 M2 로컬 환경의 개발 세트 한 라운드이며, 다른 하드웨어·Ollama 버전이나 M 프롬프트 변경 뒤에는 재측정이 필요하다. `nvidia-smi`가 없어 VRAM은 미측정이다.
