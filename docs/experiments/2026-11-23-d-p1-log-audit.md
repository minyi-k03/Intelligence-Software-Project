# D-3 P1 개발 세트 로그 점검

2026-11-23 · 담당 심동섭. B-4의 P1 개발 세트 1라운드에서 **기록된 토큰 중 출력 비중은 4.782%**였다. 최종 응답 원문과 도구 호출 인자가 없어 형식 오류율과 반복 루프 비율은 산출할 수 없다. M 개발 시험에서는 근거 장부 상세화를 먼저 검토하고 단계별 출력 상한은 설계 초기값으로 시작한다.

목적은 P1 개발 로그에서 실제로 확인되는 출력 비용·형식·반복 양상을 파악해 조건부 부품 시험 순서와 M 출력 상한 초기값을 점검하는 것이다. 이 로그는 M의 성능이나 `cap.judge` 민감도 결과를 대신하지 않는다.

## 분석 대상

B-4 제출 커밋은 `fde8dc7`, 실행 메타데이터의 커밋은 `fff578c1`이다. 실행일은 11월 22일(한국 시간)이다. Tesla T4에서 Ollama 0.40.17, `qwen2.5:7b-instruct-q4_K_M`, temperature 0, `num_ctx=8192`, `retrieval.k=5`, P1 최대 7스텝, 문항당 타임아웃 120초로 측정했다. 아래 명령으로 해당 라운드의 원본을 확인할 수 있다.

아래 수치는 `fff578c1` 실행 당시의 공통 프롬프트로 측정했다. 이후 `4a48c53`(PR #21)에서 `CONTENT_INSTRUCTION` 문구가 바뀌었다.

동결 개발 세트와 로그의 문항 ID·유형이 60건 모두 일치하며 중복·누락은 없다. 실행 메타데이터의 세 동결 파일 해시도 일치한다. 저장된 답을 재채점한 결과는 24/60이다. 비용에서만 워밍업 `hotpotqa-0040`을 제외했다. 타임아웃 `squad2-0045`, `squad2-0051`은 오답으로 집계되며, 중단 전 호출 기록은 회수되지 않았다. [측정 규칙 §7.2](../INTERFACES.md)

재현용 읽기 전용 집계는 위 `git show`로 꺼낸 JSONL의 `correct`, `is_warmup`, `calls`, `retrieved_doc_ids`를 사용한다. 정확도는 유형별 `correct=true` 건수 / 해당 유형 20문항(워밍업·타임아웃 포함)이다. 비용 지표는 워밍업 1문항을 뺀 59문항을 대상으로 하며, 기록되지 않은 타임아웃 호출을 0토큰으로 메우지 않는다. 아래 합계와 평균은 **기록된 사용량의 하한**이다. 출력 비중은 기록된 출력 토큰 합 / (기록된 입력 + 출력 토큰 합)이고, 실제 출력 비중의 하한을 뜻하지는 않는다.

## 출력 토큰 비중

각 호출의 `output_tokens` 합을 전체 기록 토큰(입력 합 + 출력 합)으로 나눴다. ‘비용 대상’은 워밍업을 제외한 문항 수, ‘호출 기록 있음’은 그중 `calls`가 남은 문항 수다.

| **전체** | **24/60** | **59** | **57** | **111** | **77,974** | **3,916** | **4.782%** |

- [측정 콜백](../../src/config/callbacks.py)은 출력 사용량 메타데이터가 없으면 응답의 단어 수를 대체값으로 쓸 수 있다. 로그에 대체 여부가 없어 위 수치는 콜백이 기록한 값으로 해석한다.

대표 사례 `hotpotqa-0049`는 네 번의 검색에서 같은 문단 ID 목록을 받았고 159출력 토큰을 기록했으나 오답이었다. 검색어와 응답 원문이 없으므로 같은 요청의 반복인지, 다른 검색어가 같은 목록으로 수렴했는지 구분할 수 없다. `hotpotqa-0048`은 정답 문단 둘이 검색 이력에 있었지만 기권했다. 근거의 연결·판정 실패 가능성을 보여 주되, 원문이 없어 원인을 확정하지 않는다. 형식 오류의 대표 사례도 원문 부재로 **선정 불가**다. 빈 답 `gsm8k-0051`을 형식 오류로 대신 세지 않는다.

## 형식 오류와 반복 루프

| 지표 | 판정 기준 | B-4에서 확인한 범위 |
|---|---|---|
| 최종 답 형식 오류율 | 마지막 비어 있지 않은 줄이 `Final answer: <답>`을 위반한 문항 수 / 원문을 확인한 문항 수 | **산출 불가.** 완료 58건 중 원문이 보존된 문항은 0건이다. 추출 답이 빈 문항은 1/58(`gsm8k-0051`)이다. |
| 반복 호출 비율 | 한 문항 안에서 도구 이름과 정규화한 인자가 앞선 요청과 같은 재호출 수 / 이력에서 확인한 전체 도구 요청 수 | **산출 불가.** 검색은 문단 ID 목록만 남고 계산기 요청과 도구별 인자가 없어 분자·분모를 복원할 수 없다. |
| 반복 루프 발생 문항 비율 | 동일 요청을 두 번 이상 낸 문항 수 / 전체 도구 이력을 확인한 문항 수 | **산출 불가.** 도구 요청 전체 이력이 보존된 문항은 0건이다. |

`parse_ok=null`은 P1의 자유 텍스트 호출에 구조화 출력 파서가 적용되지 않았다는 뜻이므로 형식 성공도 실패도 아니다. 형식 오류를 원문 또는 별도 판정값으로 확인한 문항의 분모는 0이고, 도구 이름·인자까지 확인한 문항의 분모도 0이다. **0%라는 결과가 아니다.**

P1 호출 기록에는 출력 상한(`cap`)이 설정되지 않았고 잘림 플래그도 모두 거짓이다. 따라서 **P1의 출력 상한 도달 건수는 적용 대상이 아니며**, 이 로그로 M의 단계별 상한 적절성을 판정할 수 없다.

전체 로그에서 BM25 검색 결과 목록은 51회 기록됐다. 순서까지 같은 문단 목록이 한 문항 안에서 재출현한 경우는 **11문항, 첫 출현을 제외하고 13회**였다. `hotpotqa-0049`는 네 번 모두 같은 목록을 받았다. 서로 다른 검색어도 같은 문단 목록을 반환할 수 있다.

P1의 `answer`에는 답 추출 결과만 남고 `parse_ok`는 자유 텍스트 호출에서 null이다. `loop_breaks=0`과 `budget_exhausted=false`는 기준선의 기본값이다. 형식·반복 비율을 확정하려면 같은 실행의 원문 최종 응답(또는 형식 판정값)과 문항별 도구 요청 순서·이름·인자가 필요하다. 새로 수집할 경우 별도 개발 라운드로 기록한다. [P1 구현](../../src/baselines/p1_react.py) · [기준선 결과 생성](../../src/baselines/p0.py)

## 조건부 부품 시험 순서와 상한 초기값

| 잠정 순서 | 부품 | M 개발 세트에서 확인할 사항 |
|---:|---|---|
| 1 | 근거 장부 상세화 | HotpotQA 오답 15건 중 10건은 전체 검색 이력에 정답 근거 문단 두 개가 모두 있었고, 5건은 일부가 빠졌다. 근거를 연결하고 빠진 정보를 재검색하는 부품부터 시험한다. 목표는 HotpotQA 정답 수 증가 또는 HotpotQA 문항당 호출 수 10% 감소다. |
| 2 | 동적 압축량 | 입력이 기록 토큰의 95.218%를 차지했다. 입력에는 질문·지시문·대화 이력도 들어간다. M 기본 압축과 비교해 문항당 평균 입력 토큰이 10% 줄어드는지 측정한다. |
| 3 | 간결 출력 | 수학 풀이 단계를 유지하면서 M의 문항당 평균 출력 토큰이 10% 줄어드는지 측정한다. 토큰 비중만으로 실행 시간 절감 효과는 판단할 수 없다. |

각 부품은 M 기본형과 비교해 목표를 달성하고 유형별 순정답 수가 줄지 않을 때 채택한다. 동일 도구·인자의 첫 재호출 차단은 M의 핵심 부품이며, 위 시험 순서는 조건부 부품 3개에 적용한다. [채택 기준 §6](../SPEC.md)

M의 **첫 호출 512, 계산기 후 마무리 128, 근거 판정 256토큰**을 초기값으로 유지한다. 기본 모델 호출 예산은 문항당 4회이며, 잘림 시 해당 호출의 상한을 2배로 늘린 재시도 1회는 비용에만 포함한다. P1에는 M의 단계별 상한이 적용되지 않았다. 근거 판정 상한 96·160·256의 잘림, 재시도, 정확도 비교는 M 통합 후 D-4에서 수행한다. [기본 설정](../../configs/default.yaml) · [실험 계획](../IMPLEMENTATION_PLAN.md)

## 결론과 후속 확인

출력 토큰 합계와 유형별 정확도는 확인했지만, 형식 오류율·동일 요청 반복 비율·단계 역할별 낭비는 **측정 불가**다. 같은 입력의 새 P1 개발 라운드에서 최종 응답 원문과 도구 이름·정규화 가능한 인자를 문항별로 수집해야 한다. [재측정 스크립트](../../scripts/audit_p1_dev.py), [설정](../../configs/p1_d3.yaml), [테스트](../../tests/test_audit_p1_dev.py)가 준비되어 있으나 원래 B-4 실행의 누락 데이터를 복원하지는 못한다.

**11/27 당시 재확인:** A-5b 통합 코드는 현재 브랜치에 들어왔다. 추가 P1 개발 로그 `results/runs/dev/r5/p1.jsonl`과 `r6/p1.jsonl`도 각각 60문항이지만, 두 로그 모두 `raw_final_output`과 `tool_requests` 필드가 0건이다. 따라서 형식·반복 비율의 분모는 당시 0이었다. 재측정 설정에는 최신 공통 설정 로더가 요구하는 `judge.format=json`을 추가했고, `langchain-ollama`가 없으면 결과 로그를 만들기 전에 중단하도록 고쳤다. 11/27에는 실행 환경이 없어 재측정할 수 없었으며, 필요한 수치는 아래 11/28 별도 라운드에서 새로 수집했다.
