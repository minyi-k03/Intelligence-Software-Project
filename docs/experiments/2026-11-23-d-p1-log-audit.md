# D-3 P1 개발 세트 로그 점검

2026-11-20 현재 작업 트리와 로컬에 있는 Git 참조에서 B-4의 P1 개발 세트 로그를 찾지 못했다. 분석 입력은 B-4의 `results/runs/dev/p1.jsonl` 또는 라운드별 경로 `results/runs/dev/r1/p1.jsonl`이다. 실측 지표, 조건부 부품 시험 순서, 상한 조정 판단은 로그 확보 후 확정한다.

## 집계 기준

`data/frozen/dev.jsonl`의 문항 ID와 유형을 기준으로 워밍업을 제외하고 중복, 누락, 타임아웃 수를 먼저 확인한다. 전체와 유형별로 분자·분모를 함께 남기고, 한 문항에 여러 호출이 있으면 관측 단위에 맞춰 합산한다.

| 지표 | 계산 기준 | 필요한 기록 |
|---|---|---|
| 출력 토큰 비중 | 전체 출력 토큰 합 ÷ 전체 입출력 토큰 합. 최종 답 호출을 구분할 수 있으면 최종 답 호출과 그 이전 호출의 출력 토큰도 각각 집계 | 호출별 `input_tokens`, `output_tokens`, 최종 호출 구분 |
| 형식 오류율 | 마지막 비어 있지 않은 줄이 `Final answer:` 형식이고 값이 비어 있지 않아야 한다. 이를 위반한 문항 수 ÷ 원문 최종 응답을 확인할 수 있는 문항 수 | 답 추출 전 최종 응답 또는 형식 준수 여부 |
| 반복 루프 비율 | 같은 문항에서 도구 이름과 인자가 같은 호출을 두 번 이상 요청한 문항 수 ÷ 전체 도구 호출 이력을 확인할 수 있는 문항 수. 인자 비교에 `normalize_args` 사용 | 문항별 순서가 있는 도구 이름·인자 이력 |

형식 오류 판정에는 `PipelineResult.answer`의 추출 전 원문이 필요하다. `parse_ok`는 구조화 출력의 파싱 상태다. `loop_breaks`는 루프 끊기 발동 수이므로 P1의 반복 요청을 세는 데는 도구 호출 이력이 필요하다. 관측 필드가 비어 있으면 해당 문항을 분모에서 제외하고 관측 범위를 보고한다.

## 시험 순서와 초기 상한

- 출력 토큰과 긴 응답이 주된 비용이면 간결 출력을 먼저 시험한다. 수학 풀이의 추론 단계를 유지하고, 평균 출력 토큰 10% 감소와 유형별 순정답 수 유지 여부를 확인한다.
- 반복 검색과 HotpotQA 오답이 함께 집중되면 해당 문항을 점검한 뒤 근거 장부 상세화를 우선 시험한다. 검색 문맥이 입력 토큰 비용의 대부분이면 동적 압축량을 우선 검토한다.
- 형식 오류가 자주 발생하면 간결 출력 실험 전에 원문으로 형식 준수와 잘림의 관계를 확인한다.
- `configs/default.yaml`의 상한 초기값은 첫 호출 512, 마무리 128, 근거 판정 256토큰이다. P1의 토큰 분포는 점검 단서로 사용하고, 상한 조정은 M의 개발 세트 단계별 출력 분포, 잘림·재시도, 시간과 유형별 정답 수를 비교한 뒤 판단한다.
